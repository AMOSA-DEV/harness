# Harness — Context-first Project Setup

결론부터: 프로젝트가 AI와 오래 협업하는 데 필요한 **최소 컨텍스트 구조**만 만든다.

기본 산출물은 다음과 같다.

```text
AGENTS.md
ROADMAP.md
context/
├── ABOUT-ME.md
├── BRAND-VOICE.md
├── WORKING-RULES.md
├── GLOSSARY.md
└── LESSONS.md
```

`_workspace/`는 사용자 승인 후에만 만든다. `BRIEF.md`, `HANDOFF.md`, 에이전트, 스킬, 오케스트레이터는 기본 산출물이 아니다.

## 원칙

1. 짧고 정확한 컨텍스트를 우선한다.
2. 현재 대화가 관리하는 목표와 진행 과정을 파일에 중복하지 않는다.
3. 기존 파일과 사용자가 작성한 내용은 보존한다.
4. 상태가 실제로 바뀔 때만 공통 파일을 갱신한다.
5. 병렬 작업은 공통 파일을 직접 수정하지 않는다.
6. 모르는 정보는 추정해 채우지 않는다.
7. 환경변수, API 키, 인증 정보 관련 작업은 사용자 승인 없이 수행하지 않는다.

## 시작 전 확인

프로젝트 루트에서 다음을 확인한다.

- `AGENTS.md`와 동등한 기존 지침 파일
- `ROADMAP.md` 또는 기존 작업 관리 문서
- `context/`와 유사한 장기 지식 문서
- `_workspace/`, `outputs/`, `artifacts/`, `docs/` 등 기존 산출물 구조
- Git 작업 트리의 기존 변경 사항

기존 구조가 있으면 새 구조로 강제 이동하지 않는다. 겹치는 파일의 책임을 비교하고 최소 변경안을 사용한다.

## 실행 흐름

### 1. 신규 또는 정리 판단

- 컨텍스트 구조가 없으면 **신규 구성**으로 진행한다.
- 일부 또는 전체가 있으면 **기존 구조 정리**로 진행한다.
- 사용자가 감사만 요청하면 읽기 전용으로 점검하고 파일을 수정하지 않는다.

### 2. 컨텍스트 구성

`references/context-templates.md`를 읽고 필요한 파일만 생성하거나 보완한다.

- 대화와 프로젝트 파일에서 확실히 알 수 있는 내용만 작성한다.
- 빈 항목을 채우기 위해 사용자를 장시간 인터뷰하지 않는다.
- 내용이 없는 파일은 억지로 길게 채우지 않는다.
- 기존 `BRIEF.md`와 `HANDOFF.md`는 자동 삭제하지 않는다. 더 이상 필요 없으면 이유와 대체 위치를 설명하고 사용자 요청이 있을 때만 제거한다.

### 3. Workspace 선택

`_workspace/`가 없을 때는 생성 전에 한 번만 묻는다.

> 작업 산출물 관리를 위해 `_workspace/audit`, `machine`, `human` 구조를 사용할까요? 기존 산출물 체계가 있으면 생성하지 않습니다.

다음 조건에서는 질문 없이 기존 체계를 유지한다.

- `outputs/`, `artifacts/` 등 명확한 산출물 폴더가 이미 있다.
- 코딩 프로젝트가 빌드·테스트·문서 산출물 경로를 이미 정의한다.
- 사용자가 `_workspace/`를 원하지 않는다고 말했다.

사용자가 승인하면 `references/context-templates.md`의 구조를 따른다.

### 4. 병렬 작업

공통 파일의 소유권을 분리한다.

- `AGENTS.md`: 일반 작업은 읽기 중심. 프로젝트 규칙이 바뀔 때만 수정한다.
- `ROADMAP.md`: 일반 작업은 읽기 전용. 사용자가 요청한 조정 작업만 통합 갱신한다.
- `context/`: 장기 지식이 실제로 바뀔 때만 수정한다.
- `_workspace/machine/tasks/`: 각 작업 대화가 자신의 고유 task 파일만 수정한다.

task 파일 이름은 `YYYYMMDD-task-name.md`를 사용한다. 같은 이름이 이미 있으면 짧은 식별자를 붙인다. 일반 비코딩 작업에 워크트리를 요구하지 않는다.

### 5. 검증

수정 후 `references/validation.md`를 읽고 확인한다.

최소 보고 내용:

- 생성하거나 수정한 파일
- 보존한 기존 구조
- `_workspace/` 사용 여부와 이유
- 충돌 가능성 또는 사용자가 결정해야 할 항목

## 파일 책임

| 파일 | 책임 | 갱신 시점 |
|---|---|---|
| `AGENTS.md` | 프로젝트 규칙, 중요한 경로, 검증 기준 | 규칙이 바뀔 때 |
| `ROADMAP.md` | 프로젝트 목표와 통합 작업 현황 | 조정 작업 시 |
| `context/ABOUT-ME.md` | 사용자·팀의 역할과 협업 선호 | 해당 정보가 바뀔 때 |
| `context/BRAND-VOICE.md` | 외부 표현의 문체와 금지 표현 | 문체 기준이 바뀔 때 |
| `context/WORKING-RULES.md` | 반복 적용할 작업 규칙 | 공통 규칙이 생길 때 |
| `context/GLOSSARY.md` | 도메인 용어와 약어 | 용어가 추가·변경될 때 |
| `context/LESSONS.md` | 반복 실패를 막을 장기 학습 | 재사용할 학습이 생길 때 |
| `_workspace/machine/tasks/*.md` | 개별 작업의 상태와 결과 위치 | 해당 작업 중 |

## 하지 않는 일

- 에이전트나 역할을 자동 설계하지 않는다.
- 스킬을 자동 생성하지 않는다.
- 오케스트레이터나 팀 아키텍처를 만들지 않는다.
- 런타임별 파일 구조를 대량 생성하지 않는다.
- 모든 대화가 끝날 때 공통 파일을 의무적으로 갱신하지 않는다.
- 기존 산출물 구조를 `_workspace/`로 강제 이전하지 않는다.
- 단순 질문이나 일회성 작업에 하네스를 설치하지 않는다.
