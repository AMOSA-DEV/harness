# Skill Authoring Overview

스킬은 “어떻게 수행하는가”를 담는 절차적 지식이다. 에이전트/역할 문서는 “누가 무엇을 책임지는가”를 담는다.

이 문서는 스킬 작성의 상위 설계 기준이다. description 작성 패턴, 본문 스타일, 출력 형식, script bundling, 검증 판정 같은 세부 규칙은 `core/skill-authoring-details.md`를 필요할 때 읽는다.

## 기본 구조

모든 런타임에서 스킬은 다음 정보를 가져야 한다:

1. 이름
2. 트리거 설명
3. 핵심 워크플로우
4. 입력과 출력
5. 필요한 참조 문서
6. 검증 방법
7. 실패 시 처리

런타임별 파일명, frontmatter, 경로는 `references/runtimes/{runtime}/adapter.md`를 따른다.

## Progressive Disclosure

스킬은 세 단계로 읽히도록 설계한다:

| 단계 | 내용 | 원칙 |
|---|---|---|
| Metadata | 이름과 설명 | 트리거 판단에 충분히 구체적 |
| Body | 핵심 절차 | 500줄 이내 목표 |
| References | 세부 지식 | 필요할 때만 읽도록 포인터 제공 |

## Description 작성

description은 트리거 판단의 핵심이다. 다음을 포함한다:

- 이 스킬이 처리하는 작업 유형
- 사용자가 어떤 표현을 쓰면 이 스킬을 써야 하는지
- 비슷하지만 이 스킬이 아닌 near-miss
- 후속 작업 키워드: 다시 실행, 업데이트, 수정, 보완, 이전 결과 기반

런타임마다 트리거 메커니즘이 다를 수 있으므로, “특정 모델이 보수적이다” 같은 표현은 런타임 문서에 둔다.

## 본문 작성 원칙

- 일반 원칙과 런타임 구현을 섞지 않는다.
- 반복되는 결정적 작업은 scripts로 분리한다.
- 긴 도메인 지식은 references로 분리한다.
- 한 스킬이 여러 런타임을 지원할 때는 본문에서 runtime adapter를 먼저 선택하게 한다.
- 보안 정보, 인증 정보, API 키를 요구하거나 생성하는 절차는 쓰지 않는다.

## 역할과 스킬 연결

역할은 “누가 판단하는가”를 정의하고, 스킬은 “어떻게 반복 수행하는가”를 정의한다. 역할 문서에 모든 절차를 넣으면 역할이 무거워지고, 스킬만 만들고 역할과 연결하지 않으면 오케스트레이터가 누가 어떤 절차를 써야 하는지 판단하기 어렵다.

| 연결 방식 | 적합한 경우 |
|---|---|
| 역할 문서에서 스킬 이름을 참조 | 여러 역할이나 여러 하네스에서 재사용할 절차 |
| 역할 문서에 짧게 인라인 | 해당 역할 전용이고 50줄 이하인 절차 |
| 필요 시 reference 로드 | 상세 지식이 크고 조건부로만 필요한 절차 |

오케스트레이터는 역할과 스킬의 연결표를 유지한다.

연결표에는 다음 항목을 포함한다:

| 항목 | 의미 |
|---|---|
| Role | 절차를 사용할 역할 |
| Skill | 사용할 스킬 또는 인라인 절차 이름 |
| Trigger | 어떤 조건에서 사용하는지 |
| Input | 스킬에 넘길 입력 |
| Output | 스킬이 남길 산출물 |

재사용성이 높으면 스킬로 분리하고, 특정 역할 안에서만 쓰는 짧은 절차는 인라인으로 둔다. 절차가 길지만 자주 쓰이지 않으면 별도 reference로 분리하고 역할이나 스킬에서 필요할 때 읽게 한다.
