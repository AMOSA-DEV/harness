# Runtime-Neutral Architecture Patterns

이 문서는 팀 설계 패턴을 런타임 도구명 없이 설명한다. 구현 방식은 `references/runtimes/`를 따른다.

## 공통 구성 요소

| 구성 요소 | 의미 |
|---|---|
| Orchestrator | 전체 목표를 쪼개고 순서, 산출물, 검증을 관리하는 역할 |
| Specialist | 특정 영역을 맡는 역할 |
| Reviewer | 산출물 품질과 경계면 정합성을 검증하는 역할 |
| Shared workspace | 중간 산출물을 저장하는 파일 기반 교환 장소 |
| Pointer file | 다음 세션이 하네스를 발견하게 하는 런타임별 instruction 파일 |

## 패턴

### 1. Pipeline

순차 의존 작업에 적합하다. 이전 결과가 다음 역할의 입력이 된다.

예: 요구사항 분석 → 설계 → 구현 → 검증

### 2. Fan-out/Fan-in

같은 입력을 여러 관점에서 병렬 분석한 뒤 통합한다.

예: 공식 문서 조사 + 코드 조사 + 사용자 관점 조사 → 통합 보고서

### 3. Expert Pool

입력 유형에 따라 필요한 전문가만 선택한다.

예: 리뷰 요청 내용에 따라 보안, 성능, UX, 데이터 전문가 중 일부만 실행

### 4. Producer-Reviewer

생성자와 검증자가 쌍으로 동작한다. 품질 기준이 명확한 산출물에 적합하다.

예: 초안 작성 → 검토 → 수정 → 재검토

### 5. Supervisor

작업량이 가변적일 때 중앙 역할이 파일 목록, 우선순위, 진행 상태를 보고 배분한다.

예: 대규모 마이그레이션에서 모듈별 작업 분배

### 6. Hierarchical Delegation

문제가 자연스럽게 계층으로 나뉠 때 사용한다. 깊이는 2단계 이내를 기본으로 한다.

예: 앱 리드 → 프론트엔드/백엔드 리드 → 세부 구현자

## 데이터 전달 방식

| 방식 | 적합한 경우 |
|---|---|
| 파일 기반 | 대용량 산출물, 감사 추적, 런타임 간 호환이 필요할 때 |
| 반환값 기반 | 짧은 요약이나 단발성 결과 수집 |
| 메시지 기반 | 런타임이 역할 간 직접 통신을 지원할 때 |
| 작업 목록 기반 | 런타임이 공유 task primitive를 지원할 때 |

파일 기반 전달은 모든 런타임에서 기본값으로 둔다. 메시지/작업 목록은 해당 런타임이 지원할 때만 추가한다.

## 역할 분리 기준

| 기준 | 분리 | 통합 |
|---|---|---|
| 전문성 | 판단 기준과 지식이 다름 | 같은 기준으로 처리 가능 |
| 병렬성 | 독립 실행 가능 | 강한 순차 의존 |
| 컨텍스트 | 읽어야 할 자료가 큼 | 가볍고 반복적 |
| 검증 | 독립 검토가 품질을 올림 | 검증 기준이 단순 |
| 재사용성 | 다른 하네스에서도 사용 가능 | 이번 작업 전용 |
