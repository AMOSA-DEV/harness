# Hierarchical Delegation

Hierarchical Delegation은 상위 역할이 도메인을 나누고, 도메인 리드가 하위 작업을 조율하는 팀 구조다.

```text
[총괄] -> [도메인 리드 A] -> [작업자 A1]
        [도메인 리드 B] -> [작업자 B1]
```

## 적합한 경우

- 문제가 자연스럽게 상위 도메인과 하위 작업으로 나뉜다.
- 각 도메인 안에 의미 있는 내부 조율이 필요하다.
- 평탄한 팀으로 만들면 메시지와 책임 경계가 너무 복잡해진다.

## 실행 형태

- 1단계는 협업 팀으로 두고, 2단계는 격리된 역할 호출이나 파일 기반 handoff로 처리하는 구성이 기본이다.
- 런타임이 중첩 delegation을 지원하지 않으면 평탄화한다.
- 깊이는 2단계 이내를 기본으로 한다.

## 피할 때

- 깊이가 3단계 이상 필요하면 컨텍스트 손실과 지연이 커진다.
- 런타임이 중첩 delegation을 지원하지 않으면 평탄화하거나 파일 기반 인계를 사용한다.
- 단순 병렬 작업이면 Fan-out/Fan-in이나 Supervisor가 더 낫다.

## 역할 구성

| 계층 | 역할 | 책임 |
|---|---|---|
| L0 | lead | 전체 분해, 우선순위, 최종 결정 |
| L1 | domain lead | 도메인별 설계와 하위 작업 조율 |
| L2 | worker | 경계가 명확한 세부 작업 수행 |

## 오케스트레이션

1. lead가 전체 목표를 도메인 단위로 나눈다.
2. 각 domain lead에게 목표, 범위, 완료 조건을 전달한다.
3. domain lead는 하위 작업을 직접 수행하거나 worker에게 나눈다.
4. 각 domain lead는 도메인 요약과 남은 위험을 파일로 남긴다.
5. lead가 도메인 요약을 통합한다.
6. 2단계를 기본 깊이로 두고, 더 깊어질 경우 평탄화를 검토한다.

## 구현 방식

| 방식 | 설명 | 적합한 경우 |
|---|---|---|
| 평탄화 | lead, domain lead, worker를 한 팀/흐름에 두고 작업만 계층적으로 나눈다 | 런타임이 중첩 delegation을 지원하지 않음 |
| 2단계 위임 | L0/L1은 협업하고, L2는 domain lead가 격리 호출하거나 파일로 인계한다 | 도메인 내부 하위 작업이 크지만 깊이를 제한해야 함 |
| 파일 기반 handoff | 각 계층이 요약 파일을 남기고 다음 계층이 읽는다 | 컨텍스트 손실을 줄이고 재실행 가능성을 높여야 함 |

## 권장 팀 크기

| 작업 규모 | 권장 역할 수 | 역할당 작업 수 |
|---|---|---|
| 소규모 | 2~3개 | 3~5개 |
| 중규모 | 3~5개 | 4~6개 |
| 대규모 | 5~7개 | 4~5개 |

역할이 많아질수록 조율 비용이 커진다. 역할 수를 늘리기 전에 계층을 평탄화할지, 작업을 단계별로 나눠 실행할지 검토한다.

## 실패 처리

| 상황 | 대응 |
|---|---|
| L2 worker 실패 | domain lead가 1회 재시도하거나 범위를 줄인다 |
| L1 domain lead 실패 | lead가 직접 인수하거나 사용자에게 확인한다 |
| 컨텍스트 손실 발생 | 계층을 낮추고 파일 기반 handoff를 강화한다 |

## 점검 질문

- 계층을 만든 이유가 책임 분리인지, 단순 인원 증가인지 구분됐는가?
- 각 domain lead가 최종 통합에 필요한 요약을 남기는가?
- 2단계 안에서 해결할 수 있도록 구조를 단순화했는가?
- 평탄화 방식과 2단계 위임 방식 중 어느 쪽이 런타임 제약에 맞는가?
