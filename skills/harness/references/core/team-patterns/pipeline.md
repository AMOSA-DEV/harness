# Pipeline

Pipeline은 단계가 순서대로 이어지는 팀 구조다. 이전 역할의 산출물이 다음 역할의 입력이 된다.

```text
[분석] -> [설계] -> [생성/구현] -> [검증]
```

## 적합한 경우

- 각 단계가 이전 단계의 결과에 강하게 의존한다.
- 중간 산출물을 남겨 감사하거나 부분 재실행해야 한다.
- 병렬 속도보다 단계별 품질 통제가 중요하다.

## 실행 형태

- 기본은 단일 오케스트레이터 또는 격리된 역할 호출이다.
- 순차 의존이 강하면 협업 팀의 이점이 제한적이다.
- 파이프라인 안에 독립 병렬 구간이 있으면 해당 구간만 Fan-out/Fan-in이나 협업 팀으로 바꿀 수 있다.

## 피할 때

- 여러 관점의 독립 검토가 핵심이면 Fan-out/Fan-in을 먼저 검토한다.
- 실행 중 작업 목록이 계속 늘어나면 Supervisor를 검토한다.
- 품질 검토와 재작업 루프가 핵심이면 Producer-Reviewer를 검토한다.

## 역할 구성

| 단계 | 역할 | 책임 | 입력 | 출력 |
|---|---|---|---|---|
| 1 | analyst | 목표, 제약, 요구사항 정리 | 사용자 요청, BRIEF | `_workspace/machine/01_analyst.md` |
| 2 | designer | 작업 계획이나 구조 설계 | analyst 출력 | `_workspace/machine/02_designer.md` |
| 3 | producer | 산출물 생성 또는 구현 | designer 출력 | `_workspace/machine/03_producer.md` |
| 4 | verifier | 결과 검증과 누락 확인 | producer 출력 | `_workspace/audit/04_verifier.md` |

## 오케스트레이션

1. 현재 context와 `_workspace/` 상태를 확인한다.
2. 단계별 입력과 출력 경로를 먼저 고정한다.
3. 역할을 순서대로 실행한다.
4. 각 단계가 끝날 때 다음 단계가 읽을 수 있는 파일 산출물을 남긴다.
5. 검증 실패 시 영향을 받은 이전 단계로 돌아간다.
6. 최종 결과와 남은 위험을 HANDOFF에 기록한다.

## 실패 처리

| 상황 | 대응 |
|---|---|
| 특정 단계 실패 | 1회 재시도 후 이전 단계로 되돌리거나 사용자 확인을 받는다 |
| 이전 산출물이 모호함 | 이전 단계로 돌려 구체화한다 |
| 후반 검증 실패 | producer 또는 designer 단계로 되돌린다 |
| 연쇄 지연 | 타임아웃 기준을 적용하고 부분 결과를 반환할지 판단한다 |

## 점검 질문

- 각 단계의 출력이 다음 단계의 입력으로 충분한가?
- 병목 단계가 전체 진행을 막지 않도록 쪼갤 수 있는가?
- 부분 재실행 시 어느 단계부터 다시 시작할지 명확한가?
- 병렬화할 수 있는 구간과 순차로 유지해야 하는 구간이 구분됐는가?
