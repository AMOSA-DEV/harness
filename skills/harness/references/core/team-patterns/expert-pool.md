# Expert Pool

Expert Pool은 라우터가 입력을 분류하고 필요한 전문가만 호출하는 팀 구조다.

```text
[라우터] -> {전문가 A | 전문가 B | 전문가 C}
```

## 적합한 경우

- 요청 유형이 다양하고 매번 필요한 전문성이 다르다.
- 모든 전문가를 항상 실행하면 비용이나 컨텍스트 낭비가 크다.
- 가벼운 분류 단계로 필요한 역할을 고를 수 있다.

## 실행 형태

- 기본은 격리된 역할 호출이다.
- 복합 문제에서 여러 전문가가 동시에 필요하면 Fan-out/Fan-in과 결합한다.
- 전문가끼리 발견을 공유해야 하면 협업 팀을 검토한다.

## 피할 때

- 모든 관점이 항상 필요하면 Fan-out/Fan-in을 검토한다.
- 작업 목록을 동적으로 나눠 배정해야 하면 Supervisor를 검토한다.
- 라우팅 기준이 불명확하면 오분류 위험이 커진다.

## 역할 구성

| 역할 | 책임 | 트리거 |
|---|---|---|
| router | 요청을 분류하고 필요한 전문가를 고른다 | 모든 요청 |
| expert-n | 특정 도메인을 처리한다 | router가 선택한 경우 |
| integrator | 둘 이상의 전문가 결과를 통합한다 | 복수 전문가 실행 시 |

## 오케스트레이션

1. router가 요청 유형과 필요한 전문가를 정리한다.
2. router는 선택 이유를 `_workspace/01_router_plan.md`에 남긴다.
3. 선택된 전문가만 실행한다.
4. 전문가가 하나면 결과를 바로 검증한다.
5. 전문가가 둘 이상이면 integrator가 결과를 합친다.
6. 잘못된 라우팅이 반복되면 라우팅 규칙이나 LESSONS를 갱신한다.

## 라우팅 출력 형식

라우터는 선택한 전문가와 이유를 구조화해 남긴다:

```yaml
needed_experts:
  - security-expert
  - performance-expert
reason: "요청이 인증 API의 성능과 권한 경계를 함께 다룸"
confidence: medium
skipped_experts:
  - architecture-expert
```

전문가가 필요 없다고 판단하면 그 이유도 남긴다. “선택 없음”은 실패가 아니라 라우팅 결과일 수 있다.

## 실패 처리

| 상황 | 대응 |
|---|---|
| router가 확신하지 못함 | 가장 작은 합리적 전문가 집합을 선택하거나 짧게 확인한다 |
| 선택된 전문가 실패 | 1회 재시도하거나 누락 영역을 표시한다 |
| 잘못된 전문가 선택 | 라우팅 기준을 수정하고 다음 실행에 반영한다 |
| 모든 전문가가 불필요함 | 직접 처리하거나 사용자에게 재분류 여부를 확인한다 |

## 점검 질문

- 전문가를 선택하는 기준이 사용자가 이해할 만큼 명확한가?
- 전문가를 너무 잘게 나눠 라우팅 비용이 커지지 않는가?
- 선택되지 않은 영역의 위험을 최종 결과에 표시해야 하는가?
- 라우팅 결과가 나중에 감사 가능하도록 파일로 남는가?
