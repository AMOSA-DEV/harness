# Fan-out/Fan-in

Fan-out/Fan-in은 같은 입력을 여러 역할이 독립적으로 검토한 뒤, 통합자가 결과를 합치는 팀 구조다.

```text
          -> [전문가 A] -
[입력]   -> [전문가 B]  -> [통합]
          -> [전문가 C] -
```

## 적합한 경우

- 같은 문제를 여러 관점에서 봐야 품질이 올라간다.
- 조사, 리뷰, 비교, 평가처럼 독립 병렬 작업이 가능하다.
- 최종 결과에서 상충 의견을 조정하거나 병기해야 한다.

## 실행 형태

- 역할 간 발견 공유가 결과 품질을 바꾸면 협업 팀이 가장 적합하다.
- 단순히 독립 관점의 결과만 수집하면 격리된 역할 호출로도 충분하다.
- 런타임이 직접 통신을 지원하지 않으면 각 specialist가 파일 산출물을 남기고 integrator가 합친다.

## 피할 때

- 이전 단계 결과 없이는 다음 역할이 일할 수 없으면 Pipeline을 검토한다.
- 필요한 전문가를 요청마다 선택해야 하면 Expert Pool을 검토한다.
- 통합 기준이 없으면 결과가 병렬 메모 모음으로 끝날 수 있다.

## 역할 구성

| 역할 | 책임 | 출력 |
|---|---|---|
| distributor | 입력을 관점별 작업 패킷으로 나눈다 | `_workspace/machine/01_work_packets.md` |
| specialist-n | 맡은 관점에서 독립 분석한다 | `_workspace/machine/02_specialist_n.md` |
| integrator | 결과를 합치고 충돌을 정리한다 | `_workspace/machine/03_integrated.md` |

## 오케스트레이션

1. 관점별 작업 범위와 중복 금지 영역을 정한다.
2. 각 specialist가 같은 원본 입력과 필요한 context를 읽는다.
3. 런타임이 허용하면 병렬 실행하고, 아니면 독립 프롬프트로 순차 실행한다.
4. 각 specialist는 파일 산출물을 남긴다.
5. integrator는 모든 결과를 읽고 공통점, 충돌, 우선순위를 정리한다.
6. 상충 의견은 삭제하지 않고 근거와 함께 병기한다.

## 공유해야 하는 정보

협업 팀으로 실행할 때는 모든 발견을 공유하지 않는다. 다른 역할의 조사 방향이나 판단을 바꾸는 정보만 공유한다.

| 정보 | 공유 여부 |
|---|---|
| 상충되는 근거 | 공유 |
| 다른 관점의 조사 범위를 바꾸는 발견 | 공유 |
| 최종 통합에 필요한 고신뢰 출처 | 공유 |
| 자기 관점 안에서만 쓰는 세부 메모 | 파일 산출물에만 기록 |

## 실패 처리

| 상황 | 대응 |
|---|---|
| 일부 specialist 실패 | 남은 결과로 진행하되 누락 관점을 표시한다 |
| 과반 실패 | 범위를 줄이거나 재시도 여부를 사용자에게 확인한다 |
| 결과 충돌 | 근거, 신뢰도, 출처 역할을 함께 남긴다 |

## 점검 질문

- 각 specialist의 관점이 실제로 독립적인가?
- 통합자가 판단할 우선순위 기준이 있는가?
- 병렬 실행의 이득이 조율 비용보다 큰가?
- 팀원 간 공유할 정보와 파일에만 남길 정보가 구분됐는가?
