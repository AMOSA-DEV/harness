# Supervisor

Supervisor는 중앙 역할이 작업 목록을 만들고, 우선순위와 진행 상태를 보며 워커에게 배분하는 팀 구조다.

```text
              -> [Worker A]
[Supervisor]  -> [Worker B]
              -> [Worker C]
```

## 적합한 경우

- 작업 목록이 크거나 실행 중 새 작업이 발견된다.
- 작업 단위를 배치로 나눌 수 있다.
- 진행률, 우선순위, 재배정 판단이 필요하다.

## 실행 형태

- 기본은 협업 팀이다.
- 런타임이 공유 작업 목록을 지원하지 않으면 supervisor가 파일 기반 작업 ledger를 관리한다.
- worker가 자체적으로 다음 작업을 가져갈 수 있으면 supervisor 병목을 줄일 수 있다.

## 피할 때

- 모든 작업이 고정된 독립 관점이면 Fan-out/Fan-in이 단순하다.
- 순차 의존이 강하면 Pipeline이 더 명확하다.
- supervisor가 모든 세부 판단을 직접 하면 병목이 된다.

Fan-out/Fan-in은 사전에 작업을 고정 분배하는 구조이고, Supervisor는 진행 상황을 보며 작업을 동적으로 조정하는 구조다.

## 역할 구성

| 역할 | 책임 |
|---|---|
| supervisor | 대상 목록 수집, 배치 분배, 진행 관리, 통합 |
| worker-n | 할당된 배치를 수행하고 상태를 보고 |
| verifier | 필요 시 전체 결과를 검증 |

## 오케스트레이션

1. supervisor가 대상 파일, 항목, 작업 목록을 수집한다.
2. 복잡도와 의존성을 기준으로 배치를 만든다.
3. worker에게 배치를 할당한다.
4. worker는 결과와 상태를 파일로 남긴다.
5. supervisor는 실패, 지연, 새 작업을 보고 재배정한다.
6. 모든 배치가 끝나면 통합과 최종 검증을 수행한다.

## 동적 분배 로직

1. 전체 대상 파일, 항목, 작업 목록을 수집한다.
2. 복잡도를 추정한다.
   - 파일 크기
   - import나 의존성 수
   - 변경 범위
   - 검증 난이도
3. 의존성이 있는 작업과 독립 작업을 구분한다.
4. worker가 독립 실행할 수 있는 배치 단위로 묶는다.
5. 완료 보고를 받으면 다음 배치를 할당하거나 새 작업을 추가한다.
6. 실패한 배치는 원인에 따라 같은 worker에게 재시도하거나 다른 worker에게 재배정한다.
7. 모든 작업이 끝나면 supervisor가 통합 테스트나 최종 검증을 수행한다.

## 실패 처리

| 상황 | 대응 |
|---|---|
| worker 1명 실패 | 원인 확인 후 재시도하거나 다른 worker에게 재배정한다 |
| 과반 실패 | 배치를 더 작게 나누거나 범위를 줄인다 |
| supervisor 병목 | 배치를 크게 만들고 worker 자율성을 늘린다 |
| 작업 목록 변경 | 새 배치를 추가하고 진행 상태를 갱신한다 |

## 점검 질문

- 작업 단위가 너무 작아 조율 비용이 커지지 않는가?
- worker가 독립 실행할 만큼 입력과 완료 조건이 명확한가?
- supervisor가 통합 기준과 우선순위를 갖고 있는가?
- 동적 추가 작업이 기존 우선순위와 충돌할 때 판단 기준이 있는가?
