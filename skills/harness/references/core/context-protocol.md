# Context Protocol

Context protocol은 독립적으로 실행되는 에이전트/역할이 같은 방향, 기준, 중단 조건을 공유하도록 돕는 런타임 중립 실행 규약이다.

세션별 context를 참조해 작업을 이어받고, 같은 품질 기준으로 결과를 만들고, 다음 세션이나 다른 에이전트가 이어받을 수 있는 근거를 남긴다.

## 표준 파일

| 파일 | 목적 |
|---|---|
| `context/ABOUT-ME.md` | 사용자/팀의 역할, 선호, 작업 방식 |
| `context/BRAND-VOICE.md` | 말투, 스타일, 금지 표현 |
| `context/WORKING-RULES.md` | MUST/SHOULD 규칙 |
| `context/GLOSSARY.md` | 도메인 용어 |
| `context/LESSONS.md` | 변경 이력과 학습 사항 |
| `BRIEF.md` | 현재 세션 목표 |
| `HANDOFF.md` | 완료 작업과 다음 세션 인계 |
| `ROADMAP.md` | 장기 계획 |

## 파일별 사용 시점

| 파일 | 언제 읽거나 갱신하는가 |
|---|---|
| `context/ABOUT-ME.md` | 사용자 역할, 숙련도, 커뮤니케이션 선호가 필요할 때 읽는다 |
| `context/BRAND-VOICE.md` | 사용자 대면 문장, 문서, 산출물 톤을 맞출 때 읽는다 |
| `context/WORKING-RULES.md` | 작업 전 필수 규칙, 금지사항, 완료 기준을 확인할 때 읽는다 |
| `context/GLOSSARY.md` | 도메인 용어, 약어, 파일/산출물 명칭이 모호할 때 읽는다 |
| `context/LESSONS.md` | 반복될 판단, 변경 이력, 이전 실패 패턴을 확인하거나 작업 후 갱신한다 |
| `BRIEF.md` | 이번 세션의 목표와 완료 조건을 확인할 때 읽고, 종료 시 달성 여부를 갱신한다 |
| `HANDOFF.md` | 다음 세션이 이어받을 완료 작업, 결정 사항, 남은 일을 기록한다 |
| `ROADMAP.md` | 장기 방향과 현재 우선순위를 확인하고 진행 상태를 갱신한다 |

## 역할

Context protocol은 다음 질문에 답한다:

1. 작업 전 무엇을 읽어야 하는가?
2. 이번 세션의 목표와 완료 조건은 어디서 확인하는가?
3. 장기 방향과 우선순위는 어디서 확인하는가?
4. 결과물은 어디에 어떤 형식으로 남기는가?
5. 검증 기준과 중단 조건은 어디서 확인하는가?
6. 다음 세션이나 다른 에이전트가 이어받을 정보는 어디에 남기는가?

## Pointer File

런타임별 pointer file 이름은 runtime adapter가 정한다. pointer file은 하네스의 존재와 context를 읽기 시작하는 최소 규칙만 담는다.

pointer file에 에이전트 목록, 스킬 목록, 긴 실행 규칙, 상세한 Context 관리 기준을 모두 넣지 않는다. 그것들은 오케스트레이터, 스킬/역할 문서, `context/WORKING-RULES.md`가 관리한다.

## Context 참조 규칙

pointer file에는 다음 부트스트랩 규칙을 런타임에 맞게 넣는다:

1. 작업 전 `ROADMAP.md`, `BRIEF.md`, `context/WORKING-RULES.md`를 읽는다.
2. 상세한 Context 관리 기준은 `context/WORKING-RULES.md`를 따른다.
3. 작업에 필요한 도메인/사용자/문체 정보가 있으면 `context/` 아래 관련 파일을 찾아 읽는다.

가능하면 `context/` 아래의 `.md` 파일을 스캔해 읽는다. 런타임이나 샌드박스 제약 때문에 스캔이 어렵다면 표준 파일명을 순서대로 읽는다. 없는 파일은 실패로 처리하지 말고 누락으로 기록한다.

## 초기 채우기 규칙

새 하네스를 만들 때 context 파일을 빈 템플릿으로만 두지 않는다.

1. 프로젝트 파일, 사용자 요청, 기존 문서에서 확실히 알 수 있는 내용을 채운다.
2. 확실하지 않은 항목은 추정하지 않고 `TBD`로 표시한다.
3. 사용자가 이미 작성한 내용은 보존한다.
4. 보안 정보, API 키, 인증 정보, 환경변수는 context에 요구하거나 기록하지 않는다.
5. 채운 근거가 중요한 경우 `HANDOFF.md`나 `context/LESSONS.md`에 짧게 남긴다.

사용자 숙련도와 설명 수준도 context 후보로 본다. 대화에서 기술 용어 사용, 질문의 구체성, 기존 문서의 표현 수준이 명확할 때만 `ABOUT-ME.md`나 `BRAND-VOICE.md`에 반영한다. 불확실하면 “쉬운 설명 우선, 필요 시 전문 용어 병기”처럼 안전한 기본값을 둔다.

초기화 후 사용자에게만 “직접 채워달라”고 넘기지 않는다. 먼저 자동으로 채운 내용과 `TBD`로 남긴 내용을 구분해 보고한다.

## Session Update

작업 완료 후 세션 파일 갱신 여부를 확인한다.

| 파일 | 갱신 내용 |
|---|---|
| `HANDOFF.md` | 이번 세션 완료 작업, 결정 사항, 다음 할 일 |
| `ROADMAP.md` | 진행 상태와 우선순위 변경 |
| `context/LESSONS.md` | 변경 이력, 반복될 판단, 합의, 실수 |
| `BRIEF.md` | 세션 목표 달성 여부 |

“갱신했다”고 말만 하지 말고 실제 파일을 수정한 뒤 확인한다. 단순 질문 답변처럼 세션 파일 갱신이 과한 경우에는 생략 사유를 짧게 남긴다.

세션 갱신이 필요한 작업의 종료 체크리스트:

- [ ] `HANDOFF.md`에 완료 작업, 결정 사항, 다음 할 일을 기록했다.
- [ ] `ROADMAP.md`에 완료 상태, 우선순위, 검증 계획 변경을 반영했다.
- [ ] `context/LESSONS.md`에 반복될 판단, 실수, 합의, 도메인 규칙을 기록했다.
- [ ] `BRIEF.md`에 세션 목표별 달성 여부와 미완료 사유를 기록했다.
- [ ] `_workspace/` 목적별 산출물을 삭제하지 않고 보존했으며, 필요한 경우 백업 위치를 기록했다.
