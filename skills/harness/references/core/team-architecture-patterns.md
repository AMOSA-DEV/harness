# Team Architecture Patterns

이 문서는 하네스가 생성할 에이전트/역할 팀의 실행 아키텍처를 런타임 도구명 없이 설명한다.

범위는 역할 구성, 책임 분리, 패턴 선택, 데이터 전달, 검증 흐름이다. 이 스킬 자체의 내부 구현이나 context 관리 아키텍처를 설명하는 문서가 아니다. 구현 방식은 `references/runtimes/`를 따른다.

이 문서는 상위 선택 가이드다. 패턴별 상세 기준은 `references/core/team-patterns/` 아래 문서를 함께 읽는다.

## 공통 구성 요소

| 구성 요소 | 의미 |
|---|---|
| Orchestrator | 전체 목표를 쪼개고 순서, 산출물, 검증을 관리하는 역할 |
| Specialist | 특정 영역을 맡는 역할 |
| Reviewer | 산출물 품질과 경계면 정합성을 검증하는 역할 |
| Skill | 역할이 반복해서 사용할 절차적 지식과 작업 방법 |
| Shared workspace | 중간 산출물을 저장하는 파일 기반 교환 장소 |
| Context protocol | 장기 방향, 세션 목표, 작업 규칙, 인계 정보를 공유하고 갱신하는 규약 |
| Pointer file | 런타임이 처음 읽는 상위 instruction 파일. 금지 규칙, 기본 원칙, context 진입점을 담는다. |

## 선택 기준

| 상황 | 우선 검토할 패턴 |
|---|---|
| 단계가 강하게 이어지고 이전 산출물이 다음 입력이 됨 | Pipeline |
| 같은 입력을 여러 관점에서 동시에 검토해야 함 | Fan-out/Fan-in |
| 요청 유형에 따라 필요한 전문가가 달라짐 | Expert Pool |
| 품질 기준이 명확하고 독립 검토가 중요함 | Producer-Reviewer |
| 작업 목록이 크거나 실행 중 계속 발견됨 | Supervisor |
| 문제가 자연스럽게 상위/하위 도메인으로 나뉨 | Hierarchical Delegation |

패턴은 팀의 작업 구조를 정하고, 실행 형태는 그 구조를 실제 런타임에서 어떻게 실행할지 정한다. 먼저 패턴을 고른 뒤, 역할 간 협업 필요성과 런타임 지원 범위에 따라 실행 형태를 정한다.

## 기본 패턴

### 1. Pipeline

순차 의존 작업에 적합하다. 이전 결과가 다음 역할의 입력이 된다.

예: 요구사항 분석 → 설계 → 구현 → 검증

상세 기준: `references/core/team-patterns/pipeline.md`

### 2. Fan-out/Fan-in

같은 입력을 여러 관점에서 병렬 분석한 뒤 통합한다.

예: 공식 문서 조사 + 코드 조사 + 사용자 관점 조사 → 통합 보고서

상세 기준: `references/core/team-patterns/fanout-fanin.md`

### 3. Expert Pool

입력 유형에 따라 필요한 전문가만 선택한다.

예: 리뷰 요청 내용에 따라 보안, 성능, UX, 데이터 전문가 중 일부만 실행

상세 기준: `references/core/team-patterns/expert-pool.md`

### 4. Producer-Reviewer

생성자와 검증자가 쌍으로 동작한다. 품질 기준이 명확한 산출물에 적합하다.

예: 초안 작성 → 검토 → 수정 → 재검토

상세 기준: `references/core/team-patterns/producer-reviewer.md`

### 5. Supervisor

작업량이 가변적일 때 중앙 역할이 파일 목록, 우선순위, 진행 상태를 보고 배분한다.

예: 대규모 마이그레이션에서 모듈별 작업 분배

상세 기준: `references/core/team-patterns/supervisor.md`

### 6. Hierarchical Delegation

문제가 자연스럽게 계층으로 나뉠 때 사용한다. 깊이는 2단계 이내를 기본으로 한다.

예: 앱 리드 → 프론트엔드/백엔드 리드 → 세부 구현자

상세 기준: `references/core/team-patterns/hierarchical-delegation.md`

## 복합 패턴

실전에서는 단일 패턴보다 복합 패턴이 흔하다. 복합 패턴을 사용할 때는 전체 구조를 하나로 뭉뚱그리지 말고, 어느 단계에 어떤 패턴을 적용하는지 명시한다.

| 복합 패턴 | 구성 | 적합한 경우 | 예시 |
|---|---|---|---|
| Fan-out/Fan-in + Producer-Reviewer | 여러 역할이 병렬로 산출물을 만들고, 각 산출물을 독립 검증한다 | 병렬 생성과 품질 검증이 모두 중요함 | 다국어 번역 후 언어별 리뷰 |
| Pipeline + Fan-out/Fan-in | 순차 흐름 중 특정 단계를 병렬화한다 | 전체는 단계적이지만 일부 단계는 독립 병렬 작업 가능 | 분석 → 병렬 구현 → 통합 검증 |
| Supervisor + Expert Pool | supervisor가 작업을 관리하다가 필요한 전문가를 선택 호출한다 | 작업 종류가 실행 중 달라짐 | 고객 문의 분류 후 적합한 전문가 배정 |
| Pipeline + Producer-Reviewer | 각 단계 산출물을 다음 단계로 넘기기 전에 검증한다 | 단계별 품질 게이트가 필요함 | 요구사항 검토 → 설계 검토 → 구현 검증 |
| Hierarchical Delegation + Fan-out/Fan-in | 도메인별 리드 아래에서 병렬 하위 작업을 수행한다 | 큰 도메인이 독립적이고 각 도메인 내부에 병렬 작업이 있음 | 프론트엔드/백엔드 리드가 각각 하위 작업 병렬 수행 |

복합 패턴에서는 통합 지점을 명확히 해야 한다. 병렬 결과를 누가 합치는지, 검증 실패 시 어느 단계로 되돌아가는지, 중간 산출물을 어디에 남기는지 정하지 않으면 조율 비용이 급격히 커진다.

복합 패턴의 실행 형태는 가장 협업이 많이 필요한 구간을 기준으로 정한다:

| 시나리오 | 권장 실행 형태 | 이유 |
|---|---|---|
| 리서치 + 분석 | 협업 팀 | 조사 중 발견 공유와 상충 정보 토론이 결과 품질을 바꾼다 |
| 설계 + 생성/구현 + 검증 | 협업 팀 또는 격리된 역할 호출 | 설계 변경이 구현/검증 방향을 자주 바꾸면 협업 팀, 산출물 전달만 필요하면 격리 호출 |
| Supervisor + Worker | 협업 팀 | 진행 상태, 재배정, 새 작업 발견이 자주 발생한다 |
| 생성 + 검증 | 격리된 역할 호출 또는 협업 팀 | 단순 판정은 격리 호출로 충분하고, 기준 조율이 많으면 협업 팀이 낫다 |
| 선택형 전문가 호출 | 격리된 역할 호출 | 선택된 전문가만 실행하고 결과를 모으면 충분한 경우가 많다 |

단일 역할이 완전히 격리된 단발성 작업을 수행한다면 협업 팀으로 키우지 않는다.

## 실행 형태

실행 형태는 선택한 팀 패턴을 런타임에서 수행하는 방식이다. 같은 Pipeline이라도 단일 오케스트레이터가 직접 처리할 수도 있고, 단계별 역할을 격리 호출할 수도 있다.

| 형태 | 적합한 경우 | 주의 |
|---|---|---|
| 단일 오케스트레이터 | 역할을 나눌 수는 있지만 실제로 별도 실행할 필요가 없음 | 모든 판단이 한 컨텍스트에 모여 관점 분리가 약하다 |
| 격리된 역할 호출 | 역할별 독립 실행은 필요하지만 역할끼리 직접 대화할 필요는 없음 | 오케스트레이터가 입력 전달, 결과 수집, 재시도를 모두 조율한다 |
| 협업 팀 | 역할 간 발견 공유, 상호 검증, 진행 조율이 결과 품질을 올림 | 조율 비용과 컨텍스트 비용이 커지고, 역할 간 책임 경계를 더 명확히 해야 한다 |

런타임이 직접 통신이나 공유 작업 목록을 지원하지 않으면 파일 기반 전달과 오케스트레이터 통합으로 구현한다.

패턴별 기본 실행 형태:

| 패턴 | 기본 실행 형태 | 이유 |
|---|---|---|
| Pipeline | 단일 오케스트레이터 또는 격리된 역할 호출 | 순차 의존이 강해 직접 협업 이득이 제한적 |
| Fan-out/Fan-in | 협업 팀 또는 격리된 역할 호출 | 발견 공유가 중요하면 협업 팀, 독립 관점 수집이면 격리 호출 |
| Expert Pool | 격리된 역할 호출 | 필요한 전문가만 선택 실행하는 구조 |
| Producer-Reviewer | 격리된 역할 호출 또는 협업 팀 | 단순 판정은 격리 호출, 기준 조율이 많으면 협업 팀 |
| Supervisor | 협업 팀 | 작업 할당, 진행 보고, 재배정이 계속 발생 |
| Hierarchical Delegation | 협업 팀, 격리 호출, 또는 평탄화 | 런타임의 중첩 delegation 지원 여부에 따라 달라짐 |

선택 기준:

1. 역할이 1개이거나 역할 분리가 형식적이면 단일 오케스트레이터를 쓴다.
2. 역할이 2개 이상이지만 결과 파일만 넘기면 충분하면 격리된 역할 호출을 쓴다.
3. 한 역할의 발견이 다른 역할의 작업 방향을 바꿔야 하면 협업 팀을 검토한다.
4. 협업 팀을 선택할 때는 역할별 책임, 발신/수신 정보, 충돌 처리 기준을 함께 정의한다.

의사결정 흐름:

```text
역할이 2개 이상인가?
├─ 아니오: 단일 오케스트레이터
└─ 예: 역할 간 직접 협업이 결과 품질을 바꾸는가?
   ├─ 예: 협업 팀
   └─ 아니오: 결과 파일/요약 전달만으로 충분한가?
      ├─ 예: 격리된 역할 호출
      └─ 아니오: 역할 경계와 패턴을 다시 설계
```

## 실행 구성 재편

작업 단계마다 필요한 역할 조합이 달라지면 같은 실행 구성을 끝까지 유지하지 않는다. 이전 단계의 산출물을 파일로 남기고, 다음 단계에 맞는 역할 조합으로 재편한다.

재편 절차:

1. 현재 단계의 산출물과 결정 사항을 `_workspace/`에 저장한다.
2. 다음 단계에서 필요한 역할, 스킬, 검증 기준을 다시 확인한다.
3. 이전 역할이 계속 필요하지 않으면 종료하거나 비활성 상태로 둔다.
4. 새 역할은 `_workspace/` 산출물과 context protocol을 읽고 시작한다.
5. 재편 이유와 이어받을 파일을 HANDOFF에 남긴다.

재편은 특히 Pipeline의 단계 전환, 복합 패턴의 병렬 구간 진입/종료, Hierarchical Delegation의 도메인별 작업 종료 시 유용하다.

## 팀 크기와 작업 단위

역할 수와 작업 단위는 함께 설계한다. 역할이 많아도 각 역할이 맡을 독립 작업이 충분히 크지 않으면 조율 비용만 늘어난다.

| 작업 규모 | 권장 역할 수 | 역할당 작업 수 |
|---|---|---|
| 소규모 | 1~3개 | 3~5개 |
| 중규모 | 3~5개 | 4~6개 |
| 대규모 | 5~7개 | 4~5개 |

7개를 넘는 역할이 필요해 보이면 먼저 도메인별 단계 실행, 역할 통합, Supervisor 패턴, 또는 Hierarchical Delegation의 평탄화를 검토한다.

## 데이터 전달 방식

| 방식 | 적합한 경우 |
|---|---|
| 파일 기반 | 대용량 산출물, 감사 추적, 런타임 간 호환이 필요할 때 |
| 반환값 기반 | 짧은 요약이나 단발성 결과 수집 |
| 메시지 기반 | 런타임이 역할 간 직접 통신을 지원할 때 |
| 작업 목록 기반 | 런타임이 공유 task primitive를 지원할 때 |

파일 기반 전달은 모든 런타임에서 기본값으로 둔다. 메시지/작업 목록은 해당 런타임이 지원할 때만 추가한다.

## 역할 분리 기준

역할 분리는 “사람 수를 늘리는 일”이 아니라 판단 책임과 컨텍스트 부담을 나누는 일이다. 아래 기준 중 여러 개가 동시에 해당할수록 분리하고, 하나만 약하게 해당하면 통합을 우선한다.

| 기준 | 분리 | 통합 |
|---|---|---|
| 전문성 | 판단 기준, 도메인 지식, 산출물 기준이 다름 | 같은 기준과 지식으로 처리 가능 |
| 병렬성 | 서로 다른 입력을 받아 독립 실행 가능 | 한 역할의 결과가 없으면 다른 역할이 시작할 수 없음 |
| 컨텍스트 부담 | 각 역할이 읽어야 할 자료가 크거나 서로 다름 | 읽는 자료가 작고 대부분 겹침 |
| 검증 독립성 | 만든 역할과 다른 관점의 검토가 품질을 올림 | 검증이 단순 체크리스트 수준 |
| 재사용성 | 다른 하네스나 반복 세션에서도 같은 역할을 다시 씀 | 이번 작업에서만 쓰는 임시 책임 |
| 실패 격리 | 일부 실패를 전체 실패로 만들지 않고 분리 처리할 수 있음 | 실패 시 전체 흐름을 함께 다시 봐야 함 |

역할을 분리했다면 각 역할에 대해 책임, 입력, 출력, 사용할 스킬, 실패 처리, 협업 대상, 검증 기준을 정의한다.

분리하지 않는 것이 더 나은 경우도 명시한다. 역할 이름만 다르고 같은 자료를 읽어 같은 판단을 한다면 통합한다. 분리로 얻는 품질, 속도, 재사용성보다 조율 비용이 크면 통합한다.

## 역할 정의 필수 항목

역할을 만들 때는 런타임별 파일 형식과 무관하게 다음 항목을 정의한다:

| 항목 | 내용 |
|---|---|
| 책임 | 이 역할이 판단하고 산출할 범위 |
| 비책임 | 다른 역할이나 사용자에게 남길 범위 |
| 입력 | 읽어야 할 사용자 요청, context 파일, 이전 산출물 |
| 출력 | 남길 파일, 반환 요약, 최종 산출물 기여 방식 |
| 사용할 스킬 | 반복 절차로 분리된 작업 방법 |
| 협업 대상 | 정보를 주고받을 역할과 주고받는 조건 |
| 검증 기준 | 이 역할의 산출물이 통과해야 할 기준 |
| 실패 처리 | 실패, 불확실성, 시간 초과 시 행동 |

역할 정의는 작을수록 좋지만, 책임과 입출력 경계가 빠지면 오케스트레이터가 안정적으로 조율할 수 없다.

## 역할 수 기준

팀은 전문성을 얻기 위해 나누되, 조율 비용을 감당할 수 있는 크기로 유지한다.

| 작업 규모 | 권장 역할 수 | 기준 |
|---|---|---|
| 소규모 | 1~3개 | 단일 오케스트레이터 또는 Producer-Reviewer 정도로 충분 |
| 중규모 | 3~5개 | 분석, 생성, 검증, 통합 역할을 나눌 수 있음 |
| 대규모 | 5~7개 | Supervisor나 Hierarchical Delegation을 검토 |
| 7개 초과 | 재검토 | 도메인별 단계 실행, 팀 재편, 역할 통합을 먼저 검토 |

역할 수가 많아질수록 각 역할의 책임, 출력 경로, 충돌 처리 기준을 더 명확히 해야 한다. 많은 역할이 항상 좋은 구조는 아니다.
