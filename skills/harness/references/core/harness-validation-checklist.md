# Harness Validation Checklist

검증은 런타임에 독립적인 품질 활동과 런타임별 구조 검증으로 나눈다.

## 1. 구조 검증

- 필요한 역할 문서가 모두 존재하는지 확인
- 필요한 스킬 문서가 모두 존재하는지 확인
- 오케스트레이터가 참조하는 역할/스킬 이름과 실제 파일명이 일치하는지 확인
- pointer file에 하네스 트리거와 context 참조 규칙이 있는지 확인
- 중간 산출물 경로가 `_workspace/` 아래로 정리되는지 확인
- 공통 문서에 런타임 전용 도구명이나 파일 경로가 섞이지 않았는지 확인
- 런타임별 산출물에 다른 런타임 도구명을 요구하지 않는지 확인

구체 경로와 도구명은 runtime adapter를 따른다. Core 검증은 runtime adapter를 읽었는지, 산출물이 해당 adapter의 경로 표와 실행 제약을 따르는지만 확인한다.

런타임별 추가 확인:

| 항목 | 확인 |
|---|---|
| Pointer file | 선택한 runtime adapter가 지정한 파일 이름을 사용했는가 |
| Skills/roles | 선택한 runtime adapter가 지정한 skill/role spec 경로를 사용했는가 |
| Delegation | 선택한 runtime adapter가 허용한 delegation 방식과 fallback을 함께 명시했는가 |
| Tool boundary | 다른 런타임 전용 도구명을 필수 요구로 섞지 않았는가 |

## 2. 드라이런

실행 전에 다음 질문에 답한다:

1. 첫 입력은 누가 받는가?
2. 각 역할은 무엇을 읽고 무엇을 쓰는가?
3. 다음 단계가 읽어야 하는 파일이 실제로 생성되는가?
4. 실패한 역할이 있어도 최종 결과에 누락이 표시되는가?
5. 후속 실행 때 기존 산출물을 어떻게 재사용하거나 보관하는가?
6. 병렬/delegation이 불가능할 때 메인 세션 순차 실행으로도 같은 산출물이 나오는가?
7. 부분 재실행 때 어떤 역할과 검증 범위만 다시 도는가?
8. 런타임 전용 도구가 없을 때 fallback이 같은 파일 산출물을 남기는가?
9. 세션 파일 갱신이 필요한 작업인지, 필요하다면 실제 갱신과 확인 단계가 있는가?

## 3. 트리거 검증

각 스킬마다 should-trigger와 should-not-trigger 예시를 작성한다.

- should-trigger: 실제 사용자가 말할 법한 표현 5~10개
- should-not-trigger: 키워드는 비슷하지만 다른 스킬이나 직접 답변이 맞는 표현 5~10개

near-miss가 중요하다. 명백히 무관한 예시는 테스트 가치가 낮다.

## 4. 실행 검증

가능하면 작은 샘플 작업으로 실행한다.

- 산출물이 객관적으로 검증 가능하면 assertion을 둔다.
- 주관적 산출물은 평가 기준표를 먼저 만든다.
- 개선 사항은 특정 예시에 맞춘 패치가 아니라 일반 규칙으로 반영한다.
- 새 스킬이나 크게 수정된 스킬은 with-skill과 baseline 또는 이전 iteration을 비교한다.
- 실행 테스트가 과하면 대표 프롬프트와 드라이런으로 최소 검증하고 미검증 범위를 남긴다.

## 5. 회귀 방지

변경 후 `context/LESSONS.md` 또는 런타임별 세션 파일에 다음을 기록한다:

| 날짜 | 변경 내용 | 대상 | 사유 |
|---|---|---|---|

반복 실패, 우회 작업, 같은 피드백 2회 이상은 하네스 개선 신호다.

## 6. 보안 검증

다음 항목이 있으면 실패로 본다:

- 환경변수, API 키, 토큰, 인증 정보 생성/수집/변경 절차
- 비밀 값을 context 파일이나 pointer file에 기록하라는 지시
- 인증 우회, 권한 상승, 접근 권한 변경을 하네스 기본 절차로 포함

필요한 외부 서비스 설정이 있더라도 하네스는 “사용자가 별도 보안 절차를 따른다” 수준으로만 남긴다.

## 7. 세션 갱신 검증

하네스 생성, 수정, 감사, 대규모 실행 후에는 다음을 확인한다:

- `HANDOFF.md`에 완료 작업, 결정 사항, 다음 할 일이 실제로 기록됐는가
- `ROADMAP.md`에 진행 상태나 우선순위 변경이 반영됐는가
- `context/LESSONS.md`에 변경 이력 또는 반복될 학습이 기록됐는가
- `BRIEF.md`에 세션 목표 달성 여부가 표시됐는가
- `_workspace/` 중간 산출물이 보존됐는가

작업 성격상 갱신하지 않았다면 생략 사유를 결과나 감사 파일에 남긴다.
