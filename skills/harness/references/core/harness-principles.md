# Harness Principles

이 문서는 런타임과 무관한 하네스의 공통 원칙만 다룬다. 특정 파일 경로, 도구명, 모델명은 `references/runtimes/` 아래 런타임 어댑터에서 결정한다.

## 목적

하네스는 사용자 요청을 독립 에이전트와 다음 세션이 실행할 수 있는 작업 체계로 바꾸는 메타 스킬이다.

하네스가 설계하는 작업 체계는 다음을 포함한다:

1. 프로젝트/도메인 목표에 맞게 나눈 역할과 책임
2. 역할 사이에 오가는 입력, 출력, 인계 계약
3. 각 역할이 작업 중 따라야 할 절차적 지식
4. 역할을 언제 호출하고 어떤 순서로 연결할지 정하는 오케스트레이션 흐름
5. 결과를 어떤 기준으로 검사하고 다시 개선할지 정하는 검증 루프
6. 세션과 에이전트가 목표, 범위, 진행 상태, 작업 규칙을 공유하기 위한 context protocol

## 핵심 용어

| 용어 | 의미 |
|---|---|
| 역할 | 특정 책임을 맡아 판단하고 산출물을 만드는 실행 단위 |
| 스킬 | 역할이 반복해서 사용할 절차적 지식과 작업 방법을 담은 실행 지침 |
| 오케스트레이터 | 역할과 스킬을 언제 호출하고 어떤 산출물을 넘길지 정하는 조율자 |
| Context protocol | 에이전트와 세션이 목표, 범위, 진행 상태, 작업 규칙을 공유하고 갱신하는 규약 |
| Runtime adapter | Codex, Claude Code처럼 실제 파일 이름, 경로, 호출 방식을 결정하는 구현 계층 |

## 분리 원칙

| 층 | 질문 | 산출물 |
|---|---|---|
| Core | 무엇을 설계해야 하는가? | 역할, 책임, 데이터 흐름, 검증 기준, context protocol |
| Runtime | 어디에 어떤 형식으로 구현하는가? | instruction 파일, 파일 경로, delegation 방식, 런타임별 호출 규칙 |
| Templates | 어떤 파일 형식으로 남기는가? | BRIEF, HANDOFF, ROADMAP, context 파일 템플릿 |

Core 문서에는 특정 런타임의 경로, pointer file, delegation 도구명을 넣지 않는다.

## 공통 설계 절차

새로 구축하든 기존 구조를 재편하든 다음 순서를 따른다:

1. 사용자 요청에서 목표, 도메인, 주요 작업 유형을 파악한다.
2. 런타임을 감지하거나 사용자 지정 런타임을 우선한다.
3. 먼저 런타임과 무관한 Core 설계를 만든다.
4. Core 설계에는 역할, 입출력 계약, 절차적 지식, 오케스트레이션, context protocol, 검증 기준을 포함한다.
5. Core 설계를 선택한 런타임의 파일 이름, 경로, 호출 방식으로 옮긴다.
6. 구현 후 구조 검증, 드라이런, 트리거 검증, 산출물 품질 검증을 수행한다.

## 신규 구축 기준

새 하네스를 처음 만들 때는 문서를 분류하는 대신, 공통 설계 절차를 다음 산출물로 구체화한다:

1. 목표, 도메인, 주요 작업 유형 요약
2. 역할 목록과 역할별 책임
3. 역할별 입력, 출력, 인계 계약
4. 역할별 절차적 지식과 스킬 분리 여부
5. 역할 호출 순서와 산출물 흐름
6. 작업 전후에 읽고 갱신할 context protocol
7. 완료 조건, 검증 기준, 중단 조건
8. 선택한 런타임이 실제로 읽을 instruction 파일과 템플릿

신규 구축에서도 Core, Runtime, Templates의 분리 원칙은 유지한다. 먼저 런타임과 무관한 작업 체계를 정하고, 그 뒤 선택한 런타임의 파일 이름, 경로, 도구 호출 방식으로 옮긴다.

## 산출물 품질 기준

- 독립 에이전트와 새 세션이 바로 이어서 실행할 수 있어야 한다.
- 역할 문서와 스킬 문서는 서로 중복하지 않는다.
- 런타임별 산출물은 해당 런타임이 실제로 읽거나 사용할 수 있는 형식이어야 한다.
- 중간 산출물은 `_workspace/audit/`, `_workspace/machine/`, `_workspace/human/`으로 목적별 분리해 감사, 재실행, HUMAN 검토가 가능해야 한다.
- 새 실행으로 기존 `_workspace/`를 교체해야 하면 삭제하지 말고 timestamp 백업 경로에 전체 보존한 뒤 백업 위치를 기록해야 한다.
- 보안 정보, API 키, 인증 정보의 생성, 수집, 변경, 노출, 저장 절차는 포함하지 않는다.

## 기존 자료 감사 기준

이미 운영 중인 하네스나 관련 문서가 있을 때 사용한다. 여기서 감사는 문서의 좋고 나쁨을 평가하는 일이 아니라, 기존 자료가 어떤 성격의 지식인지 분류하고 어디에 남길지 판단하는 일이다.

감사 대상은 기존 pointer file, 역할 문서, 스킬 문서, context 파일, 런타임별 instruction, 설계 메모, 예시 문서다.

이 기준의 목적은 기존 문서를 그대로 복사하는 것이 아니라, 런타임과 무관한 설계 원칙, 런타임별 구현, context protocol, 템플릿, 예시, 제거 대상을 구분하는 것이다.

기존 자료의 각 문단을 다음 중 하나로 분류한다:

| 분류 | 기준 | 정리 방향 |
|---|---|---|
| `core` | 역할 분해, 데이터 흐름, 검증 등 런타임 무관 원칙 | Core reference로 남긴다 |
| `runtime-specific` | 특정 도구, 경로, 모델명, instruction 파일 | 해당 런타임 adapter 기준으로 남긴다 |
| `context-protocol` | 세션 관리, 사용자/브랜드/규칙/용어 컨텍스트의 실행 규약 | Core의 하위 개념으로 남긴다 |
| `template` | BRIEF, HANDOFF, ROADMAP, context 파일의 작성 형식 | Template reference로 남긴다 |
| `example` | 특정 도메인 예시 | 런타임 무관 예시와 런타임별 예시로 분리 |
| `obsolete` | 현재 설계와 충돌하거나, 더 정확한 문서로 대체됐거나, 같은 내용을 반복하는 낡은 내용 | 삭제하거나 필요 시 변경 이력으로만 남긴다 |

단순 문자열 치환은 금지한다. 먼저 문단의 추상 개념을 뽑고, 그 뒤 런타임별 구현으로 나눈다.
