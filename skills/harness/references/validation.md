# Harness Validation

결론부터: 파일 존재 여부보다 각 파일의 책임과 병렬 수정 경계를 확인한다.

## 구조

- `AGENTS.md`가 짧은 프로젝트 규칙과 context 진입점만 담는가?
- `ROADMAP.md`가 프로젝트 목표와 통합 현황만 담는가?
- `context/`에 장기적으로 반복 사용할 정보만 있는가?
- `BRIEF.md`와 `HANDOFF.md`를 새로 만들지 않았는가?
- 에이전트, 스킬, 오케스트레이터를 만들지 않았는가?

## 보존

- 사용자가 작성한 기존 내용을 덮어쓰지 않았는가?
- 기존 `outputs/`, `artifacts/`, 문서 체계를 강제 이전하지 않았는가?
- 기존 변경 사항과 무관한 파일을 수정하지 않았는가?

## Workspace

- `_workspace/`를 만들기 전에 사용자의 승인을 받았는가?
- 승인했다면 `audit/`, `human/`, `machine/tasks/`가 구분됐는가?
- 병렬 작업은 고유한 task 파일만 수정하는가?
- 일반 작업이 `ROADMAP.md`를 직접 수정하지 않는가?

## 내용

- 추정한 사용자 정보, 명령, 도메인 용어가 없는가?
- 현재 대화의 상세 실행 기록을 공통 context에 복제하지 않았는가?
- 환경변수, API 키, 인증 정보가 포함되지 않았는가?
- 각 파일에 같은 규칙이 불필요하게 반복되지 않는가?

## 대표 시나리오

1. 빈 프로젝트: 최소 컨텍스트 구조안을 만들고 `_workspace/` 생성 여부를 묻는다.
2. 기존 프로젝트: 기존 지침과 산출물 경로를 보존하며 누락된 컨텍스트만 보완한다.
3. 병렬 작업: 각 작업이 별도 task 파일을 사용하고 공통 파일은 조정 작업만 수정한다.
4. 감사 요청: 파일을 수정하지 않고 책임 중복, 누락, 충돌 위험만 보고한다.

## Near-miss

다음 요청에는 이 스킬을 적용하지 않는다.

- 단순 기능 구현이나 버그 수정
- 일회성 문서 작성
- 에이전트 또는 스킬 하나만 만들어 달라는 요청
- API 키, 인증, 환경변수 설정 요청
- 프로젝트 구조와 무관한 일반 질문
